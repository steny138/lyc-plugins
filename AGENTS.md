# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, etc.) when working with code in this repository.

## What this repo is

A Claude Code plugin marketplace of **mods**: plugins whose function hooks draw live UI (panes, buttons) inside the Claude Code terminal. `.claude-plugin/marketplace.json` lists every plugin, and each plugin lives in `plugins/<name>/`. When adding a plugin, register it in both marketplace.json and the table in README.

## Commands

```sh
claude plugin validate plugins/sudoku   # manifest, hooks and types contract
claude plugin test plugins/sudoku       # run every *.test.ts / *.test.tsx in that folder
claude plugin validate .                # the marketplace manifest
```

There is no npm, build or lint step. `claude plugin test` cannot filter to a single test: it only takes a plugin folder and runs all of its test files.

Type-check a plugin with `npx -y -p typescript tsc -p plugins/<name>` once Claude Code has loaded it (loading generates `.claude-plugin/types/`). `plugins/sudoku-online/service/server.ts` is outside that check: it uses `node:` modules and the template has no Node types.

### Trying a mod in a live session

- `claude --plugin-dir plugins/<name>` loads a plugin from the repo for one session.
- Hot reload (via the `plugin-authoring` skill) only watches the session's dev-mods folder. **A symlink placed there loads once but never reloads**: neither editing the files it points to nor recreating the symlink triggers a reload. Put a real copy there (`rsync -a --exclude '.claude-plugin/types' plugins/<name>/ <dev-mods>/<name>/`) and re-sync after each change.
- A reload unloads the module: module variables (timers) are gone, `$.state` values survive, `session.start` fires again, and children started with `$.process.spawn` are killed.

## Mod architecture

- `types` in `plugin.json` points to `types/index.d.ts`, which declares the plugin's state types via `declare module 'claude-code' { interface PluginState { ... } }`. `hooks/hooks.json` lists the hooks modules to load.
- A hooks module exports `register: Register` and registers hooks with `on(event, filter?, hook)`: slash commands are registered on `session.start`, handled on `command.run`, and `ui.render` (`component: 'Pane'`) returns the JSX view. State is read and written through `atom({ plugin, key })` with `read` / `update`, scoped to the session.
- All engine APIs live on `$` (EngineInterface). The mod runtime has **no DOM and no Node**: the only way out is through APIs such as `$.http.fetch`, `$.process.*` and `$.clock.*`. For the full API, load the `plugin-authoring` skill; its bundled `claude-code.d.ts` holds the type definitions.
- `.claude-plugin/types/`, which `tsconfig.json` extends, is generated by Claude Code when it loads the mod. It is gitignored; never edit or commit it by hand.
- Keep pure logic apart from the engine: e.g. `sudoku.ts` is engine-free pure functions (a board is an 81-character string, `.` for a blank), while `register.tsx` handles UI and state.

## Testing

- Tests import `test` / `describe` / `expect` / `mock` from `claude-code/testing`. Like hooks, the test environment has no filesystem, network or child processes.
- Fake engine-level behavior (command registration, `ui.open` / `ui.close` / `ui.panes`) with `on(...)` hooks beneath the plugin; see `stubEngine` in `register.test.ts`. Mount the view with `$.ui.mount`, then drive it with `find` / `findAll` / `press`, locating elements by `key` (e.g. `cell-<i>`, `digit-<d>`).
- Tests observe external behavior through commands, buttons and the view, not internal state layout.

## Domain docs

- `CONTEXT.md`: the glossary for sudoku-online (LAN Sudoku races). Follow its terms when discussing or implementing the race feature (e.g. write 「共同服務」, not 「服務端」).
- `docs/adr/`: architecture decision records.
- `.scratch/` holds draft specs (e.g. `.scratch/sudoku-online/spec.md`). It is excluded only via the local `.git/info/exclude`; never stage or commit it.
